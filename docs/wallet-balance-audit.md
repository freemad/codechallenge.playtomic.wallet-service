# Wallet balance audit

The wallet service appends an exact signed Decimal128 posting to `wallet_ledger` in the same local transaction as each successful credit or debit, its per-wallet sequence increment, operation finalization and balance event. Replays, denied spends, uncommitted changes, payment reservations and receipts are not postings. The ledger ID is the opaque wallet ID plus `:` plus its decimal sequence. Only the wallet writer should have insert access to the ledger; deny updates and deletes to runtime principals. There is no history endpoint or automatic balance repair.

## Enroll wallets prospectively

1. Back up the named database. Stop all old writers and recovery workers; do not mix writer versions. Roll out the ledger-writing version everywhere. Enrollment requires a verified opening balance, not an inference from legacy operation records. No wallet is automatically certified or provisioned.
2. While writers are paused, run `deployment/enroll-wallet-audit.js` with `mongosh` against the intended replica-set database for each approved wallet. Provide `AUDIT_WALLET_ID`, `AUDIT_CURRENCY` and exact decimal `AUDIT_OPENING` from the signed-off opening evidence. A mismatch, missing wallet or repeat enrollment fails. Keep the approval evidence separately. The script anchors the amount to the existing sequence (zero before the first posting); prior periods are not covered.
3. Resume writers. The first cut-off is the next 00:00 UTC. A separate deployment may run the same wallet image with `WALLET_AUDIT_ENABLED=true` and `SPRING_MAIN_WEB_APPLICATION_TYPE=none`; leave the flag off on request-serving pods if desired. Provision `wallet.audit.alerts.v1` or set `WALLET_AUDIT_TOPIC` and configure `SPRING_KAFKA_BOOTSTRAP_SERVERS`. Disable unrelated workers in the audit deployment.

## What a checkpoint proves

The schedule is persisted per wallet. Each tick claims due work oldest first rather than depending on an invocation at midnight. At the last Mongo logical timestamp **before** the cut-off second, a primary snapshot read returns the persisted currency, balance and sequence. A transaction committing at or after the boundary belongs to the next period, regardless of when its provider call started. Keep replica-set clocks synchronized. The worker sums the verified opening and immutable postings through the snapshot sequence with exact `BigDecimal` arithmetic and checks sequence continuity and currency. This is not a comparison with the wallet at worker start.

On agreement, the result transaction writes `calculatedBalance`, `auditedLedgerSequence`, `cutoffAt`, and `calculationTimestamp` on the wallet and advances the schedule one UTC day. `balance` is untouched. The transaction checks the claim token, expected cut-off and lease before making any change. An expired worker cannot commit after takeover. On disagreement it blocks that wallet's schedule instead, writes protected evidence to `wallet_balance_audit`, and enqueues an opaque alert in `wallet_audit_alert_outbox`. Other wallets can continue. Investigate blocked wallets against trusted evidence; do not edit ledger rows or advance a checkpoint to silence an alert.

**Historical retention is a deployment requirement.** Configure MongoDB's `minSnapshotHistoryWindowInSeconds` on all eligible replica-set members to exceed the longest supported outage **plus** backlog processing time. The usual minutes-long default is not adequate for delayed daily accounting. Budget disk and test catch-up at the expected volume. If the snapshot is unavailable, the worker emits `audit.run_failed` and leaves the period due; it never falls back to today's balance. Recovery outside retention requires trusted point-in-time backups or archived cut-off evidence and operator intervention. Monitor oldest due cut-off, blocked schedules, snapshot history and unpublished alert age independently, including while all workers are down.

## Monitoring boundary

A discrepancy emits `audit.balance_discrepancy` at ERROR after the result commits. Its Kafka alert contains only `schemaVersion: 1`, `eventType: WalletBalanceDiscrepancy` and `eventId` (also the Kafka key and the protected audit document ID). No wallet identifiers or money are included. Restrict access to the evidence collection. Broker acknowledgment precedes the fenced outbox acknowledgment. Retries after a crash may publish twice: deduplicate by `eventId` in the monitoring consumer. Kafka acceptance is not pager delivery; deployment owns the consumer, ACLs, topic retention, routing and escalation. `audit.alert_delivery_incomplete` reports a failed relay attempt. A stopped broker does not undo a checkpoint or erase pending evidence.
